> 狀態：v1。這份文件專門給「開場先想讓聽眾聽懂」的演示開場：系統、角色、流程、演示切法、漏洞意義、修補意義一次過。

## 1. 這是什麼系統

這是一個**多角色退款審批的受控測試系統**，模擬一個內部服務單／退款審核流程。它的重點不是功能多複雜，而是**角色、組織、狀態與資源關係要分明**，方便拿來討論業務邏輯漏洞與修補。

系統刻意做了幾個設計：

- 零外部依賴（Node 24 內建 `node:sqlite`），不靠額外套件跑。
- 有 GUI（可黑箱操作）也有 API（可觀測流量）。
- 種子資料是決定性的：兩個 tenant（`acme`、`globex`），每 tenant 都有 customer、supervisor、finance。
- 狀態機明確：退款從 `REQUESTED` 走到 `REFUNDED` 要經過審核與核准。
- 恢復機制明確：`reset`、`snapshot`、`restore`、`verify` 一鍵回歸乾淨狀態。

> **【第一年】** 黑箱只靠 GUI 與可觀測 API 觀察行為，不讀原始碼、不碰內部 instrumentation。
> **【第二年】** 會進到原始碼裡面，把行為對齊到程式位置。
> **【第三年】** 會在 vulnerable／fixed 兩版之間跑修補與驗證。

## 2. 有哪些使用者

| 角色 | 身份範圍 | 能做的事 |
| --- | --- | --- |
| Customer（例：acme-alice） | 申請者 | 建立自己的退款、查詢自己的退款 |
| Supervisor（例：acme-carol） | 核准人（同 tenant） | 審核、核准、拒絕同一 tenant 的退款 |
| Finance（例：acme-dave） | 財務執行人（同 tenant） | 執行已核准的退款 |
| 背景 Worker | 非即時背景程序 | 輪詢執行「已核准」的退款，防漏做／重複做 |

每個人都屬於一個 tenant（`acme` 或 `globex`）。不同 tenant 的人，本來就不該看到別 tenant 的資料。

> **【第一年】** 測試時會用不同角色登入，觀察不同角色能看到什麼。
> **【第二年】** 會看同一份行為，找到「哪一層該管角色／tenant 關係沒管好」。
> **【第三年】** 會用這些角色關係去驗證補丁有沒有真的卡住越權，而且沒壞正常操作。

## 3. 正常流程應該怎麼跑

正常退款流程：

1. Customer 建立退款申請 → 狀態 `REQUESTED`
2. Supervisor 審核 → 狀態 `REVIEWED`
3. Supervisor 核准 → 狀態 `APPROVED`
4. Finance 或背景 Worker 執行退款 → 狀態 `REFUNDED`
5. 重新查詢，看到最終狀態

這條流程背後其實有兩條隱藏原則：

- **狀態要按順序走**：不能從 `REQUESTED` 直接變 `REFUNDED`，不能沒有審核就核准。
- **有人能碰某個資源，是有條件的**：Customer 看自己的、Supervisor 看同一個 tenant 的、Finance 看同一個 tenant 且已核准的。

> **【第一年】** 會建構這條合法軌跡，作為行為模型比對的「正常行為」參考。
> **【第二年】** 會看這條軌跡，把它的步驟對齊到真正的 handler 與 predicate。
> **【第三年】** 會用這條軌跡做功能保存驗證：修補後正常流程還是要過。

## 4. 我們把演示切成哪些狀況

這次演示刻意分三段：

1. **合法流程（normal）**
   - 證明系統本身有正常行為，流程是看得出來的。
2. **違規掃描（vulnerable）**
   - 證明在漏洞模式下，同一個人換 id 去看別人的退款是看得到的。
3. **修補對照（fixed）**
   - 在固定模式下，同樣的掃法，結果被擋住，且不洩漏別人的資料存在與否。

這種切法不是為了秀操作順序，而是為了搭配下面兩個問題的答案：

- **「系統本來應該怎麼防？」** ← 第 1 段給你正常行為與規格。
- **「現在哪裡破了？」** ← 第 2 段給你與正常行為的差異。
- **「修好了沒差嗎？」** ← 第 3 段給你修補前後對照。

> **【第一年】** 合法軌跡 + 違規掃描一起構成行為證據。
> **【第二年】** 會把這兩段行為證據對齊到程式，找出缺口。
> **【第三年】** 會拿漏洞版與固定版對照去驗證補丁。

## 5. 剛才演示的情境，為什麼算漏洞

情境是這樣：

- acme-alice 登入，她的合法身份只有自己的退款（這次是 id 1 與 id 4）。
- 她掃 id 1..20，跳過自己的 id，結果：
  - 同一個 tenant 裡面，別人的退款（例如 bob 的 id 2）被讀到了。
  - 跨 tenant 的退款（例如 globex 的 id 3）也被讀到了。

算漏洞的原因是：

- Alice 不該看 bob 的退款，也不該看 globex 的退款。
- 系統回了「別人的退款細節」，而且還包含 `owner_id`、`tenant_id`、金額、狀態等其他人的資料。
- 這不是前端畫面問題或回應排版問題，而是**存取約束沒生效**，符合我們計畫裡面講的典型業務邏輯漏洞之一：**不該看的東西看得到**。

> **【第一年】** 會把這個行為當成「違規軌跡」收下，作為 black-box 發現的證據。
> **【第二年】** 會從這裏面推出違反了什麼安全不變量，並往程式裡面找執行位置。
> **【第三年】** 會把這個不變量補回去，並驗證其他替換方式也被擋住、且正常流程沒壞。

## 6. 這種漏洞會有什麼問題

從三個層次講：

1. **資料權限錯位**
   - 顧客本來只能看自己的退款，現在可以讀同一個 tenant 別人的退款，甚至跨 tenant 的退款。
   - 違反了「本人才該看本人資料」的最小原則。
2. **隱私與機密資訊外洩**
   - 讀到的回應裡面會有金額、狀態、申請原因、擁有者帳號等等，不只是「有沒有」，還有內容。
   - 退款資料通常涉及財務與客戶資訊，不能隨意讓別人看得到。
3. **為小洞 leading to 更大問題**
   - 一旦能讀別人的 id 與基本欄位，後續可能組合其他嘗試（例如試找可利用的資源、或構造後續操作）。
   - 所以我們計畫把這種漏洞放在第一個可重現例子裡面，做行為推論 → 定位 → 修補的串聯練習。

> **【第一年】** 會用這個案例證明行為模型推論能抓到違規行為。
> **【第二年】** 會用這個案例練習缺失定位。
> **【第三年】** 會把這個案例分級，作為單一 enforcement point 的基線案例（待 v2 補上 worker-bypass 多 hunk 案例後，再跑多 hunk 練習）。

## 7. 修復後為什麼解決了問題

當我們換到固定版（`--fixed`），發生的事是：

- acme-alice 還是可以登入，還是可以看到自己的退款 id 1、id 4。
- 但她掃 1..20、跳過自己的 id，結果：
  - 同 tenant 其他人可讀：0 筆
  - 跨 tenant 可讀：0 筆
  - 全部被擋，回 404，且回應不說明「這筆有沒有」之類的額外線索。

修復之所以解決問題，是因為：

- **所有權與 tenant 約束回來了**：Customer 只能看自己的，Supervisor／Finance 只能看同一個 tenant 內部的。
- **同一條操作被阻擋**：不是換個 id 就逃掉，而是「本來不該看的，通通攔住」。
- **不額外洩漏資訊**：回 404，不確認目標是否存在，所以攻擊者拿不到額外線索。

> **【第一年】** 會拿漏洞版與固定版對照，做為可重現的行為證據。
> **【第二年】** 會從這個對照裡面，把缺失約束對齊到程式位置。
> **【第三年】** 會拿這個對照去驗證補丁：阻擋攻擊＋保留合法流程。
